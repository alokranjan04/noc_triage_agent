# 01 — Requirements

Acceptance criteria use **EARS** style (WHEN … THE SYSTEM SHALL …). Each criterion has an id `REQ-x.y` used in tests, evals and commits.

---

## REQ-1 — Check cell KPIs
**User story:** As a NOC engineer, I want to ask for a cell's latest KPIs, so that I can see quickly whether it is healthy.

| Id | Acceptance criterion |
| --- | --- |
| REQ-1.1 | WHEN the user gives a valid cell id (`CELL-NNNN`) that exists, THE SYSTEM SHALL return the latest KPIs: drop call rate, PRB utilization, availability, throughput, plus site, region and window end time. |
| REQ-1.2 | WHEN the KPIs are returned, THE SYSTEM SHALL list every breached KPI with its value and threshold (see REQ-2). |
| REQ-1.3 | WHEN the cell id is well-formed but does not exist, THE SYSTEM SHALL return `error_code = CELL_NOT_FOUND` and the agent SHALL tell the user and ask them to check the id. No ticket is created. |
| REQ-1.4 | WHEN the user's cell id does not match `CELL-NNNN`, THE agent SHALL ask for a valid id in that format **without calling any tool**. The tool SHALL also reject it with `error_code = INVALID_CELL_ID` (defense in depth). |
| REQ-1.5 | WHEN the user asks only for information ("don't open a ticket"), THE agent SHALL NOT call `create_ticket`. |

## REQ-2 — Breach rules (deterministic)
**User story:** As a NOC lead, I want consistent breach rules, so that every engineer and the agent judge cells the same way.

| Id | Acceptance criterion |
| --- | --- |
| REQ-2.1 | THE SYSTEM SHALL treat these as breaches (strictly worse than threshold): drop call rate **> 2.0%**; PRB utilization **> 85.0%**; availability **< 99.0%**; throughput **< 5.0 Mbps**. Values exactly at the threshold are **not** breaches. |
| REQ-2.2 | THE SYSTEM SHALL compute `suggested_priority`: **P1** if availability < 95.0%; else **P2** if any breach; else **NONE**. |
| REQ-2.3 | Breach and priority logic SHALL live in code (`rules.py`) and be unit tested; the LLM SHALL NOT be relied on to compute them. |

## REQ-3 — Create tickets safely
**User story:** As a NOC engineer, I want the agent to open a ticket with the right priority when a cell is breaching, so that the right team acts quickly.

| Id | Acceptance criterion |
| --- | --- |
| REQ-3.1 | WHEN a cell has `suggested_priority` P1 or P2 and the user asks to triage or open a ticket, THE agent SHALL call `get_cell_kpis` first and then `create_ticket` with that priority. |
| REQ-3.2 | THE `create_ticket` tool SHALL re-check the cell's KPIs itself and reject a priority that the rules don't justify: P1 without availability < 95% → `PRIORITY_NOT_JUSTIFIED`; P2 with no breach → `PRIORITY_NOT_JUSTIFIED`. |
| REQ-3.3 | P3 (informational) tickets SHALL be allowed on any existing cell, but the agent SHALL create one only when the user explicitly asks for a low-priority/informational ticket. |
| REQ-3.4 | WHEN an open ticket already exists for the cell, THE `create_ticket` tool SHALL NOT create another; it SHALL return `status = exists` with the existing ticket id, and the agent SHALL tell the user that ticket id. |
| REQ-3.5 | Ticket ids SHALL be deterministic: `TCK-` + the 4 digits of the cell id (e.g. `CELL-1002` → `TCK-1002`). |
| REQ-3.6 | THE ticket summary SHALL be generated by code from the breached KPIs (values and thresholds), max 200 characters. `create_ticket` SHALL have no free-text parameter, and text supplied by the user SHALL NOT change the priority (prompt-injection resistance). |
| REQ-3.7 | Tickets created in a conversation SHALL be stored in **session state**, so each conversation (and each eval case) starts from the same fixture tickets. |

## REQ-4 — Explain decisions
| Id | Acceptance criterion |
| --- | --- |
| REQ-4.1 | THE agent's final answer SHALL state: the cell id, whether it is healthy or breaching, each breached KPI with value vs threshold, and the action taken (ticket id + priority, existing ticket id, or "no ticket"). |
| REQ-4.2 | THE answer SHALL be concise (≤ 120 words) and SHALL NOT invent KPI values or ticket ids not returned by tools. |

## REQ-5 — Safety and scope
| Id | Acceptance criterion |
| --- | --- |
| REQ-5.1 | WHEN the user asks for a network change (reboot, reconfigure, reset, disable), THE agent SHALL decline, explain it can only check KPIs and open tickets, and offer to do that. It SHALL NOT call tools in that turn. |
| REQ-5.2 | WHEN the user pressures for a higher priority than the rules allow (e.g. "it's down, open a P1"), THE agent SHALL check KPIs and follow the rules, explaining the evidence. |
| REQ-5.3 | WHEN the user asks about several cells, THE agent SHALL check each cell and handle each one independently. |

## REQ-6 — Engineering, evaluation and deployment
| Id | Acceptance criterion |
| --- | --- |
| REQ-6.1 | Unit tests (pytest) SHALL cover REQ-1.1–1.4, REQ-2.x and REQ-3.2–3.7 without calling an LLM or the network. |
| REQ-6.2 | An ADK evalset with the 15 cases in `evals/cases.yaml` SHALL run with `adk eval` and meet the targets in `00-overview.md`. |
| REQ-6.3 | Model id, project and region SHALL come from environment variables. |
| REQ-6.4 | The agent SHALL run in `adk web` locally and be deployed to Agent Runtime or Cloud Run with test data packaged inside the agent folder. |
| REQ-6.5 | The README SHALL show how to run, test, evaluate and deploy, with the eval results table. |
